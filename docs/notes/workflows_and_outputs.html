Workflows and outputs

Curated example workflows and formatted-fit reporting patterns for sblr

1 Overview

This note describes the recommended high-level workflows for the unreleased sblr package and links them to the curated example scripts in examples/workflows/. The workflows connect the model interfaces, data representations, and posterior outputs described elsewhere in these notes. They are intended to demonstrate the public API, the main model families, and compact ways to inspect fitted models.

The workflows are runnable demonstrations and validation templates. They are not necessarily lightweight package examples: real runs may need external PLINK BED data, a prepared Glist, local output paths, native code, multiple threads, and longer MCMC chains. Demonstration-scale settings are useful for checking that inputs align, native samplers execute, and outputs format correctly; they should not be interpreted as final inference.

The current intended architecture is:

Glist + phenotype or summary statistics
    -> make_summary_stats()
    -> make_sparse_ld()
    -> stblr_csr(), stblr_bed(), or stblr_csr_annot()
    -> check_stblr_consistency()
    -> summarise_posterior(), summarise_components(), summarise_architecture()
    -> make_credible_sets()

Internally, C++ backends return stblr_raw objects that are validated against stblr_raw_schema and then converted to stable formatted fit objects by the canonical R formatter. User-facing workflows should normally work with the formatted fit object, not with raw backend output.

4 Workflow scripts as executable architecture documents

A workflow script serves several roles at once:

  1. It demonstrates a complete object handoff across public functions.
  2. It records marker-order, sample-row, scaling, and LD settings that must remain consistent.
  3. It provides an integration check that independently developed package layers compose correctly.
  4. It supplies compact inspection patterns for objects that may contain tens of thousands or millions of marker rows.

It does not replace function help, automated tests, or a study-specific analysis plan. Help pages define individual arguments. Tests should verify small deterministic contracts. Workflow scripts instead show how realistic, potentially expensive pieces are assembled.

Before running a workflow, replace local data paths, confirm selected sample and marker order, choose an LD output prefix that can be written safely, and decide whether the demonstration-scale MCMC settings are appropriate for the immediate purpose.

5 Data requirements

Most workflows expect a package-specific Glist object and a phenotype vector or matrix y. For demonstration runs, the scripts can read a small example Glist from an environment-configured directory:

Sys.setenv(SBLR_EXAMPLE_DATA_DIR = "path/to/example/data")

The directory should contain a file such as:

Glist_sparseLD_1k.RDS

Heavy or benchmark-style sections should remain disabled by default and should be gated by:

Sys.setenv(SBLR_RUN_HEAVY_EXAMPLES = "true")

The examples should avoid private absolute paths. If a workflow requires local project data, use environment variables or clearly marked placeholders.

6 Basic CSR workflow

The basic CSR workflow is the canonical entry point. It demonstrates how to go from a Glist object and phenotype data to summary statistics, sparse LD, fitted CSR models, and posterior summaries.

library(sblr)
source("examples/workflows/00_workflow_helpers.R")

Glist <- read_example_glist()

sim <- mtsim(
  Glist = Glist,
  chr = 1,
  rsids = Glist$rsidsLD[[1]],
  nt = 3,
  n_shared = 30,
  n_specific = 10,
  h2 = c(0.4, 0.5, 0.3),
  rg = matrix(c(1.0, 0.7, 0.3,
                0.7, 1.0, 0.5,
                0.3, 0.5, 1.0), nrow = 3, byrow = TRUE),
  re = 0,
  seed = 1
)

y <- as.matrix(scale(sim$y))

stats <- make_summary_stats(
  Glist = Glist,
  y = y,
  chr = 1,
  nthreads = 1
)

Glist <- make_sparse_ld(
  Glist = Glist,
  out_prefix = file.path(tempdir(), "sblr_basic_ld"),
  chr = 1,
  max_distance_variants = 1000,
  r2_threshold = 0.001,
  block_size = 1024,
  nthreads = 1
)

fit_csr_bayesc <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesC",
  nit = 1000,
  nburn = 500,
  seed = 1
)

check_stblr_consistency(fit_csr_bayesc)

BayesR can be fitted through the same wrapper by changing method:

fit_csr_bayesr <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesR",
  nit = 1000,
  nburn = 500,
  seed = 1
)

check_stblr_consistency(fit_csr_bayesr)

7 Sparse-LD and BED workflows

The sparse-LD/BED workflow compares summary-statistics CSR models with individual-level BED models. Use this workflow when checking that the two data interfaces behave as expected on the same simulated or real phenotype data.

The complete data and alignment contracts are documented in Sparse-LD and BED workflows.

The practical stages are:

BED-backed Glist + phenotypes
    -> align LD markers with BED columns using match()
    -> optionally fit stblr_bed()
    -> compute stats with make_summary_stats()
    -> compute sparse LD with make_sparse_ld()
    -> fit stblr_csr()
    -> compare BED and CSR summaries cautiously

7.1 Prepare BED, Glist, and phenotype inputs

The workflow loads a Glist, selects chromosomes and markers, and obtains or simulates a phenotype matrix. mtsim() is useful for integration checks because its returned effects and causal markers provide known truth. In a real analysis, phenotypes and covariate adjustment should follow the study analysis plan.

Map selected LD-marker identifiers back to BED marker columns using match():

cls <- match(Glist$rsidsLD[[chr]], Glist$rsids[[chr]])
stopifnot(!anyNA(cls))

This is a correctness check, not bookkeeping. The same selected markers and order must be used for BED fitting, sufficient statistics, sparse LD, and posterior interpretation.

7.2 Compute sufficient statistics and sparse LD

make_summary_stats() computes the marker-trait and phenotype cross-products used by the CSR model from a BED-backed Glist. Important returned quantities include:

  • stats$wy, marker-trait cross-products;
  • stats$ww, marker diagonal cross-products;
  • stats$yy, phenotype sums of squares;
  • metadata such as marker count, trait count, and sample size when available.

make_sparse_ld() writes thresholded sparse LD from the same BED-backed Glist and stores the sparse-LD prefix, selected chromosomes, marker columns, allele frequencies, rows, threshold, window, and block metadata in Glist$sparseLD. Report r2_threshold, distance limits, selected rows, allele frequencies, marker columns, and scaling assumptions.

7.3 Fit and compare CSR and BED models

fit_csr_bayesc <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesC",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

fit_bed_bayesc <- stblr_bed(
  y = y,
  Glist = Glist,
  method = "bayesC",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10,
  nchains = 1
)

check_stblr_consistency(fit_csr_bayesc)
check_stblr_consistency(fit_bed_bayesc)

Matched BED and CSR fits should agree qualitatively when marker order, selected rows, genotype scaling, priors, and MCMC settings match. Exact equality is not expected. Sparse-LD thresholding, residual representation, update scheduling, floating-point behavior, and Monte Carlo variation can all produce differences. Compare posterior effects, PIPs, and variance summaries; do not treat equality of individual draws as a validation target.

For BayesR/SBayesRC-style models, inspect component summaries:

summarise_components(fit_csr_bayesr)

8 Annotation-informed models

The annotation workflow demonstrates both annotation-unaware and annotation-aware CSR models. It starts from the same CSR preparation path, then compares annotation prior families while holding stats, sparse LD, and marker order fixed.

Supported examples include:

  • annotation-unaware CSR BayesC and BayesR with stblr_csr();
  • fixed annotation-informed BayesC priors with annotation_model = "prior";
  • learned annotation effects with annotation_model = "learned";
  • grouped BayesC priors with annotation_model = "group";
  • SBayesRC-style annotation-dependent BayesR component probabilities with annotation_model = "sbayesrc".

The workflow stages are:

mtsim_annotation()
    -> summarize_annotation_signal()
    -> make_summary_stats()
    -> make_sparse_ld()
    -> align annotation matrix A
    -> fit fixed, learned, group, and SBayesRC-style CSR models with stblr_csr_annot()
    -> compact fit, marker, variance, and annotation summaries

8.1 Simulate and inspect annotation signal

mtsim_annotation() simulates multi-trait phenotypes, marker effects, overlapping annotation memberships, enriched causal-marker sampling, and marker-specific prior values. It is useful because the annotation architecture and causal markers are known.

Before fitting, summarize_annotation_signal(sim) reports annotation size, causal-marker counts, and causal rates. These are truth-aware simulation diagnostics. They are unavailable in real data, where causal membership is not known.

8.2 Prepare shared CSR inputs and align annotations

A marker annotation matrix should have markers in the same order as the sparse-LD marker order and fitted marker-level posterior summaries:

marker_id <- Glist$rsidsLD[[1]]
A <- sim$annot
rownames(A) <- marker_id

stopifnot(
  nrow(A) == length(marker_id),
  identical(rownames(A), marker_id)
)

Row i of A must describe the same marker as row i of stats$wy, stats$ww, the sparse-LD rows and columns, and the returned marker-level posterior summaries.

8.3 Fit annotation prior families

Fixed annotation-informed priors:

fit_prior <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = list(
    A = A,
    fixed_pi_marker = sim$pi_marker,
    fixed_vb_multiplier = sim$vb_multiplier,
    use_pi_marker = TRUE,
    use_vb_multiplier = TRUE
  ),
  annotation_model = "prior",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_prior)

Learned annotation effects:

fit_learned <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = A,
  annotation_model = "learned",
  learn_pi_annot = TRUE,
  learn_vb_annot = TRUE,

  nburn = 100,

check_stblr_consistency(fit_learned)

Grouped BayesC priors:

names(group) <- rownames(A)

fit_group <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = group,
  annotation_model = "group",
  group_names = c("annotated", "background"),
  group_pi_init = c(0.002, 0.001),
  group_vb_multiplier_init = c(1.1, 1.0),
  updatePi = TRUE,
  updateGroupVb = TRUE,
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_group)

SBayesRC-style annotations:

fit_sbayesrc <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = A,
  annotation_model = "sbayesrc",
  gamma = c(0, 0.01, 0.1, 1),
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_sbayesrc)
summarise_components(fit_sbayesrc)

The SBayesRC-style model uses annotation-dependent probabilities over an exact null and multiple active variance components. It is not an exact reproduction of the published GCTB SBayesRC implementation as exposed by default: sblr uses a CSR sparse-LD likelihood and defaults to gamma = c(0, 0.01, 0.1, 1). Users who want the published gamma grid can supply:

gamma = c(0, 0.001, 0.01, 0.1, 1)

Matching that grid aligns one part of the prior specification; it does not make the complete implementation identical to GCTB SBayesRC. See Annotation-informed models for the model comparison.

CSR SBayesRC also supports optional BayesS-style selection_s. Sampled trait-specific selection_s is requested through the unified annotation interface:

fitS <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = annotations,
  annotation_model = "sbayesrc",
  estimate_selection_s = TRUE
)

Sampled selection_s is not supported for annotation_model = "prior", "learned", or "group". See selection_s implementation status for the complete support matrix and defaults.

9 LD-swap diagnostics and fine-mapping

LD-swap diagnostics are enabled through updateLDswap = TRUE. The fitted object contains stable ld_swap and ld_swap_chains fields. If diagnostics are not available or not applicable, these fields should be present with NULL values.

fit_csr_ldswap <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesR",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10,
  updateLDswap = TRUE,
  ld_swap_prob = 0.50,
  ld_swap_r2 = 0.001,
  ld_swap_moves = 20
)

check_stblr_consistency(
  fit_csr_ldswap,
  require_ld_swap = TRUE
)

fit_csr_ldswap$ld_swap

Credible sets are post-processing outputs constructed from fitted model outputs and LD information. They are not separate sampler return objects.

cs <- make_credible_sets(
  fit = fit_csr_ldswap,
  Glist = Glist,
  trait = "D1",
  coverage = 0.95,
  min_r2 = 0.5,
  pip_cutoff = 0.001,
  locus_pip_cutoff = 0.01,
  max_locus_distance = 1e6,
  method = "pip"
)

cs$summary
cs$sets[[1]]

make_credible_sets() extracts marker PIPs from fit$dm, then uses supplied dense LD or Glist$sparseLD slices to build regional credible sets. It accepts optional marker sets; otherwise it defines loci around high-PIP markers. The returned object contains summary, sets, locus_sets, loci, parameters, and the resolved trait.

make_credible_sets() delegates per-locus set construction to make_credible_sets_from_ld(). Within a locus, it repeatedly selects a lead marker, forms a candidate set using LD to the lead marker, ranks candidate members by PIP, and includes markers until the requested coverage is reached. Because no maximum number of sets is exposed by make_credible_sets(), one locus may produce multiple sets labelled CS1, CS2, and so on. With allow_incomplete = FALSE, under-coverage attempts are dropped rather than returned with an incomplete flag.

extract_stblr_finemap_loci() and finemap_stblr_csr() return their own post-processing objects and may include credible-set outputs when requested, but those are helper-level diagnostics, not native sampler return fields.

12.1 Annotation-specific components

Annotation-aware fits add fields whose interpretation depends on the prior family:

  • Fixed-prior models may expose marker-specific prior inclusion probabilities, prior variance multipliers, and compact annotation summaries.
  • Learned annotation models expose learned eta_pi and/or eta_vb quantities where those updates were enabled, together with acceptance summaries.
  • Group models expose group-level inclusion and variance summaries, such as group_pi, group_vb_multiplier, and group_nincluded where returned.
  • SBayesRC-style models expose annotation effects on component probabilities. The alpha fields describe annotation effects for probit stick-breaking steps, sigmaSqAlpha summarizes their variance parameters, comp_prob contains marker-level posterior component probabilities, and ncomp summarizes numbers of markers assigned to components.
  • In CSR BayesR, the null component column is usually component_0 and dm = 1 - P(component_0).
  • In CSR SBayesRC, the null component column is usually gamma_0.00 and dm = 1 - P(gamma_0.00).

These components have different dimensions and meanings. Do not compare an eta_pi coefficient directly with an alpha coefficient without accounting for their distinct links and prior structures.

13 Posterior, component, and architecture summaries

Posterior summaries should be based on formatted fit objects:

post <- summarise_posterior(fit_csr_bayesc)
head(post)

plot_posterior(post)

BayesR and SBayesRC-style component summaries:

components <- summarise_components(fit_csr_bayesr)

Architecture summaries can be used to inspect how signal relates to MAF, prior scaling, PIP, or sampled selection_s behaviour. When providing MAF, align by marker ID using match() rather than %in% so marker order is preserved:

idx <- match(Glist$rsidsLD[[1]], Glist$rsids[[1]])

arch <- summarise_architecture(
  fit = fit_csr_bayesc,
  maf = maf_ld,
  min_pip = 0.01,
  top_n = 20
)

14 Compact reporting

Marker-level matrices can contain tens of thousands or millions of entries. Printing fit$bm, fit$dm, fit$b, a full comp_prob, or the complete fit object floods the console and obscures useful diagnostics. Full objects should remain available for analysis and serialization, while routine reporting should aggregate them deliberately.

A compact trait-level summary can include:

  • number of markers and traits;
  • sum of PIPs by trait, colSums(fit$dm);
  • mean absolute posterior effect, colMeans(abs(fit$bm));
  • means and selected quantiles of vbs, vgs, and ves;
  • compact diagonal and off-diagonal covariance summaries when present.

For example:

data.frame(
  trait = colnames(fit$dm),
  pip_sum = colSums(fit$dm),
  mean_abs_bm = colMeans(abs(fit$bm)),
  mean_vg = colMeans(fit$vgs),
  mean_ve = colMeans(fit$ves)
)

Treat sum(PIP) as an effective posterior number of included markers under the fitted model, not as a known count of causal variants.

15 PIPs and top-marker summaries

For marker i and trait t, fit$dm[i, t] represents PIP or non-null posterior probability under the fitted likelihood, prior, and sampler. A useful top-marker table contains marker identifier, trait, PIP, absolute posterior mean effect, and signed posterior mean effect:

ord <- order(-fit$dm[, 1], -abs(fit$bm[, 1]))
head(data.frame(
  marker = rownames(fit$dm),
  pip = fit$dm[, 1],
  abs_bm = abs(fit$bm[, 1]),
  bm = fit$bm[, 1]
)[ord, ], 10)

Rankings depend on LD, the marker set, priors, phenotype architecture, summary-statistic quality, and MCMC settings. Correlated markers can share posterior evidence, and an annotation-informed prior can change rankings even when the likelihood is unchanged. Top markers are candidates for follow-up, not automatically causal variants.

When comparing models, report whether the same markers, traits, LD, and MCMC settings were used. Differences in rankings otherwise combine model effects with input differences.

16 Variance and covariance summaries

vgs and ves provide iteration-level genetic and residual variance summaries. vbs tracks the active marker-effect variance scale used by the model. Report posterior means together with quantiles or trace diagnostics, not only final values.

In simulations, compare posterior genetic and residual variance summaries with the generating architecture and requested h2. Do not expect exact recovery from a short chain or finite simulated data. Realized simulated heritability, sparse-LD approximation, prior shrinkage, and Monte Carlo variation all affect the comparison.

For multiple traits, covb, covg, and cove summarize different covariance targets when returned. Their off-diagonal entries should be interpreted only after confirming that the fitted wrapper actually represents the intended joint model. Parallel single-trait fits do not automatically become a fully joint multi-trait analysis.

17 Annotation-level diagnostics

Annotation diagnostics answer different questions depending on whether truth is available and how annotation information enters the prior.

17.1 Simulation truth and posterior summaries

For an mtsim_annotation() result:

summarize_annotation_signal(sim)
summarize_annotation_signal(sim, fit)

The first call summarizes true annotation sizes and causal enrichment. The second adds annotation-level mean PIP and mean absolute posterior effects for each trait. Comparing these tables helps assess recovery in simulations, but does not establish causal annotation effects in real data.

17.2 Learned and group annotation fits

For learned models, inspect eta_pi and eta_vb together with posterior marker summaries, annotation prevalence, and correlations among annotation columns. Large coefficients can reflect true enrichment, overlap, collinearity, weak regularization, or short-chain instability.

For group models, report group sizes alongside group_pi, group_vb_multiplier, and group_nincluded. Small groups generally produce less stable group-level summaries.

17.3 SBayesRC-style prior-architecture diagnostics

The exported helpers convert SBayesRC-style annotation coefficients into component probabilities and expected gamma multipliers:

  • sbayesrc_annotation_pi() and sbayesrc_annotation_gamma_mean() summarize individual annotation coefficient rows;
  • sbayesrc_marker_pi() and sbayesrc_marker_gamma_mean() combine complete marker annotation profiles with alpha.

Annotation-row summaries are not the same as marker-level predictions when annotations overlap. A compact report can show the annotation-level expected gamma table, summary() of marker expected gamma, and its correlation with PIP by trait. These describe the fitted prior architecture and posterior relationship; they are not proof that an annotation or marker is causal.

See Technical annotation priors and Technical SBayesRC-style annotations for the underlying prior structures.

18 Demonstration versus production runs

The workflow scripts use short, often single-chain settings to test integration and make iterative development feasible. A successful demonstration run shows that inputs align, native samplers execute, and outputs can be formatted. It does not establish convergence or robust inference.

Production analyses generally require:

  • substantially longer burn-in and retained sampling;
  • repeated chains or otherwise defensible convergence assessment;
  • trace, mixing, effective-sample-size, and posterior predictive diagnostics;
  • sensitivity analysis for prior settings and annotation regularization;
  • sensitivity to LD thresholds, LD windows, scaling, and marker selection;
  • reproducible seeds, software versions, and input provenance;
  • held-out validation or cross-fitting where data-derived priors are reused.

No universal chain length can be recommended from the current workflows. Required effort depends on marker count, sparsity, LD, prior complexity, annotation collinearity, and the inferential target.

19 Recommended validation and reporting checklist

For real analyses, run a small or moderate validation first and save:

  • package git commit hash;
  • model call;
  • sessionInfo();
  • dimensions: markers, traits, samples if BED, LD nonzeros if available;
  • nit, nburn, nthin, nchains, ncores;
  • runtime and object size if available;
  • check_stblr_consistency(fit);
  • key posterior summaries;
  • warnings and diagnostics.

For each reported fit, also record:

  • Data source: BED source or summary-statistics provenance, selected chromosomes/regions, marker count, and marker-order checks.
  • Samples and traits: sample size n, selected sample rows, number of traits, phenotype preprocessing, and missingness handling.
  • LD construction: source panel, r2_threshold, distance limits, scaling, block settings, and CSR prefix provenance.
  • Model and priors: wrapper name, plain or annotation-informed prior, inclusion and variance-prior settings, annotation preprocessing, group definitions, gamma grid where relevant, and whether fixed global or sampled trait-specific selection_s was used.
  • MCMC settings: nit, nburn, nthin, chains, seed, scheduling choices, and thread count.
  • Convergence caveat: diagnostics performed and any limitations caused by short or single-chain runs.
  • Marker summaries: PIP sums, top-marker table, and selected posterior effect summaries without dumping full matrices.
  • Variance summaries: posterior means and uncertainty for genetic, residual, and active marker-effect variance quantities.
  • Annotation summaries: annotation size, enrichment or learned coefficients, group summaries, or SBayesRC-style component diagnostics when relevant.
  • Validation and sensitivity: BED-versus-CSR comparison, simulation truth, held-out prediction, prior sensitivity, and LD-threshold sensitivity as appropriate.

At minimum, inspect:

check_stblr_consistency(fit)
summary(colMeans(fit$dm, na.rm = TRUE))
summary(colMeans(fit$bm, na.rm = TRUE))
summary(colMeans(fit$vgs, na.rm = TRUE))
summary(colMeans(fit$ves, na.rm = TRUE))
fit$ld_swap

For annotation-informed analyses, explicitly state that enrichment and posterior prioritization are evidence structures rather than causal proof.

For large analyses, object size and trace storage may become the limiting factor. Use the workflow examples to identify which fields are needed for the intended post-processing before adding long chains or many traits.

# Overview

This note describes the recommended high-level workflows for the unreleased `sblr`
package and links them to the curated example scripts in `examples/workflows/`.
The workflows connect the model interfaces, data representations, and posterior
outputs described elsewhere in these notes. They are intended to demonstrate the
public API, the main model families, and compact ways to inspect fitted models.

The workflows are **runnable demonstrations and validation templates**. They are
not necessarily lightweight package examples: real runs may need external PLINK
BED data, a prepared `Glist`, local output paths, native code, multiple threads,
and longer MCMC chains. Demonstration-scale settings are useful for checking that
inputs align, native samplers execute, and outputs format correctly; they should
not be interpreted as final inference.

The current intended architecture is:

```text
Glist + phenotype or summary statistics
    -> make_summary_stats()
    -> make_sparse_ld()
    -> stblr_csr(), stblr_bed(), or stblr_csr_annot()
    -> check_stblr_consistency()
    -> summarise_posterior(), summarise_components(), summarise_architecture()
    -> make_credible_sets()
```

Internally, C++ backends return `stblr_raw` objects that are validated against
`stblr_raw_schema` and then converted to stable formatted fit objects by the
canonical R formatter. User-facing workflows should normally work with the
formatted fit object, not with raw backend output.

# Workflow decision table

Choose the workflow from the available data and the intended prior, not from
which script is shortest. The model map in [Model overview](model_overview.html)
separates data representation, trait structure, and prior structure.

|---|---|---|---|
| Fit from summary statistics and sparse LD | `stats` and sparse-LD metadata in `Glist` | `stblr_csr()` | CSR ST-BLR fit |
| Fit directly from individual-level PLINK genotypes | BED-backed `Glist`, phenotype matrix, aligned marker columns | `stblr_bed()` | BED ST-BLR fit |

# Workflow scripts as executable architecture documents

A workflow script serves several roles at once:

1. It demonstrates a complete object handoff across public functions.
2. It records marker-order, sample-row, scaling, and LD settings that must remain consistent.
3. It provides an integration check that independently developed package layers compose correctly.
4. It supplies compact inspection patterns for objects that may contain tens of thousands or millions of marker rows.

It does **not** replace function help, automated tests, or a study-specific
analysis plan. Help pages define individual arguments. Tests should verify small
deterministic contracts. Workflow scripts instead show how realistic, potentially
expensive pieces are assembled.

Before running a workflow, replace local data paths, confirm selected sample and
marker order, choose an LD output prefix that can be written safely, and decide
whether the demonstration-scale MCMC settings are appropriate for the immediate
purpose.

# Data requirements

Most workflows expect a package-specific `Glist` object and a phenotype vector or
matrix `y`. For demonstration runs, the scripts can read a small example `Glist`
from an environment-configured directory:

```r
Sys.setenv(SBLR_EXAMPLE_DATA_DIR = "path/to/example/data")
```

The directory should contain a file such as:

```text
Glist_sparseLD_1k.RDS
```

Heavy or benchmark-style sections should remain disabled by default and should be
gated by:

```r
Sys.setenv(SBLR_RUN_HEAVY_EXAMPLES = "true")
```

The examples should avoid private absolute paths. If a workflow requires local
project data, use environment variables or clearly marked placeholders.

# Basic CSR workflow

The basic CSR workflow is the canonical entry point. It demonstrates how to go
from a `Glist` object and phenotype data to summary statistics, sparse LD, fitted
CSR models, and posterior summaries.

```r
library(sblr)
source("examples/workflows/00_workflow_helpers.R")

Glist <- read_example_glist()

sim <- mtsim(
  Glist = Glist,
  chr = 1,
  rsids = Glist$rsidsLD[[1]],
  nt = 3,
  n_shared = 30,
  n_specific = 10,
  h2 = c(0.4, 0.5, 0.3),
  rg = matrix(c(1.0, 0.7, 0.3,
                0.7, 1.0, 0.5,
                0.3, 0.5, 1.0), nrow = 3, byrow = TRUE),
  re = 0,
  seed = 1
)

y <- as.matrix(scale(sim$y))

stats <- make_summary_stats(
  Glist = Glist,
  y = y,
  chr = 1,
  nthreads = 1
)

Glist <- make_sparse_ld(
  Glist = Glist,

  block_size = 1024,

)

fit_csr_bayesc <- stblr_csr(

```

# Sparse-LD and BED workflows

The sparse-LD/BED workflow compares summary-statistics CSR models with
individual-level BED models. Use this workflow when checking that the two data
interfaces behave as expected on the same simulated or real phenotype data.

The complete data and alignment contracts are documented in
[Sparse-LD and BED workflows](sparse_ld_and_bed_workflows.html).

The practical stages are:

```text
BED-backed Glist + phenotypes
    -> align LD markers with BED columns using match()
    -> optionally fit stblr_bed()
    -> compute stats with make_summary_stats()
    -> compute sparse LD with make_sparse_ld()
    -> fit stblr_csr()
    -> compare BED and CSR summaries cautiously
```

## Prepare BED, `Glist`, and phenotype inputs

The workflow loads a `Glist`, selects chromosomes and markers, and obtains or
simulates a phenotype matrix. `mtsim()` is useful for integration checks because
its returned effects and causal markers provide known truth. In a real analysis,
phenotypes and covariate adjustment should follow the study analysis plan.

Map selected LD-marker identifiers back to BED marker columns using `match()`:

```r
cls <- match(Glist$rsidsLD[[chr]], Glist$rsids[[chr]])
stopifnot(!anyNA(cls))
```

This is a correctness check, not bookkeeping. The same selected markers and order
must be used for BED fitting, sufficient statistics, sparse LD, and posterior
interpretation.

## Compute sufficient statistics and sparse LD

`make_summary_stats()` computes the marker-trait and phenotype cross-products used
by the CSR model from a BED-backed `Glist`. Important returned quantities include:

- `stats$wy`, marker-trait cross-products;
- `stats$ww`, marker diagonal cross-products;
- `stats$yy`, phenotype sums of squares;
- metadata such as marker count, trait count, and sample size when available.

`make_sparse_ld()` writes thresholded sparse LD from the same BED-backed `Glist`
and stores the sparse-LD prefix, selected chromosomes, marker columns, allele
frequencies, rows, threshold, window, and block metadata in `Glist$sparseLD`.
Report `r2_threshold`, distance limits, selected rows, allele frequencies, marker
columns, and scaling assumptions.

## Fit and compare CSR and BED models

```r
fit_csr_bayesc <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesC",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

fit_bed_bayesc <- stblr_bed(
  y = y,
  Glist = Glist,
  method = "bayesC",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10,
  nchains = 1
)

check_stblr_consistency(fit_csr_bayesc)
check_stblr_consistency(fit_bed_bayesc)
```

Matched BED and CSR fits should agree qualitatively when marker order, selected
rows, genotype scaling, priors, and MCMC settings match. Exact equality is not
expected. Sparse-LD thresholding, residual representation, update scheduling,
floating-point behavior, and Monte Carlo variation can all produce differences.
Compare posterior effects, PIPs, and variance summaries; do not treat equality of
individual draws as a validation target.

For BayesR/SBayesRC-style models, inspect component summaries:

```r
summarise_components(fit_csr_bayesr)
```

# Annotation-informed models

The annotation workflow demonstrates both annotation-unaware and annotation-aware
CSR models. It starts from the same CSR preparation path, then compares annotation
prior families while holding `stats`, sparse LD, and marker order fixed.

Supported examples include:

- annotation-unaware CSR BayesC and BayesR with `stblr_csr()`;
- fixed annotation-informed BayesC priors with `annotation_model = "prior"`;
- learned annotation effects with `annotation_model = "learned"`;
- grouped BayesC priors with `annotation_model = "group"`;
- SBayesRC-style annotation-dependent BayesR component probabilities with
  `annotation_model = "sbayesrc"`.

The workflow stages are:

```text
mtsim_annotation()
    -> summarize_annotation_signal()
    -> make_summary_stats()
    -> make_sparse_ld()
    -> align annotation matrix A
    -> fit fixed, learned, group, and SBayesRC-style CSR models with stblr_csr_annot()
    -> compact fit, marker, variance, and annotation summaries
```

## Simulate and inspect annotation signal

`mtsim_annotation()` simulates multi-trait phenotypes, marker effects,
overlapping annotation memberships, enriched causal-marker sampling, and
marker-specific prior values. It is useful because the annotation architecture
and causal markers are known.

Before fitting, `summarize_annotation_signal(sim)` reports annotation size,
causal-marker counts, and causal rates. These are truth-aware simulation
diagnostics. They are unavailable in real data, where causal membership is not
known.

## Prepare shared CSR inputs and align annotations

A marker annotation matrix should have markers in the same order as the sparse-LD
marker order and fitted marker-level posterior summaries:

```r
marker_id <- Glist$rsidsLD[[1]]
A <- sim$annot
rownames(A) <- marker_id

stopifnot(
  nrow(A) == length(marker_id),
  identical(rownames(A), marker_id)
)
```

Row `i` of `A` must describe the same marker as row `i` of `stats$wy`, `stats$ww`,
the sparse-LD rows and columns, and the returned marker-level posterior summaries.

## Fit annotation prior families

Fixed annotation-informed priors:

```r
fit_prior <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = list(
    A = A,
    fixed_pi_marker = sim$pi_marker,
    fixed_vb_multiplier = sim$vb_multiplier,
    use_pi_marker = TRUE,
    use_vb_multiplier = TRUE
  ),
  annotation_model = "prior",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_prior)
```

Learned annotation effects:

```r
fit_learned <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = A,
  annotation_model = "learned",
  learn_pi_annot = TRUE,
  learn_vb_annot = TRUE,
  rw_sd_eta_pi = 0.02,
  rw_sd_eta_vb = 0.02,
  annot_update_every = 10,
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_learned)
```

Grouped BayesC priors:

```r
group <- ifelse(A[, 1] != 0, "annotated", "background")
names(group) <- rownames(A)

fit_group <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = group,
  annotation_model = "group",
  group_names = c("annotated", "background"),
  group_pi_init = c(0.002, 0.001),
  group_vb_multiplier_init = c(1.1, 1.0),
  updatePi = TRUE,
  updateGroupVb = TRUE,
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_group)
```

SBayesRC-style annotations:

```r
fit_sbayesrc <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = A,
  annotation_model = "sbayesrc",
  gamma = c(0, 0.01, 0.1, 1),
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10
)

check_stblr_consistency(fit_sbayesrc)
summarise_components(fit_sbayesrc)
```

The SBayesRC-style model uses annotation-dependent probabilities over an exact
null and multiple active variance components. It is not an exact reproduction of
the published GCTB SBayesRC implementation as exposed by default: `sblr` uses a
CSR sparse-LD likelihood and defaults to `gamma = c(0, 0.01, 0.1, 1)`. Users who
want the published gamma grid can supply:

```r
gamma = c(0, 0.001, 0.01, 0.1, 1)
```

Matching that grid aligns one part of the prior specification; it does not make
the complete implementation identical to GCTB SBayesRC. See
[Annotation-informed models](annotation_informed_models.html) for the model
comparison.

CSR SBayesRC also supports optional BayesS-style `selection_s`. Sampled
trait-specific `selection_s` is requested through the unified annotation
interface:

```r
fitS <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = annotations,
  annotation_model = "sbayesrc",
  estimate_selection_s = TRUE
)
```

Sampled `selection_s` is not supported for `annotation_model = "prior"`,
`"learned"`, or `"group"`. See [selection_s implementation status](selection_s_status.md)
for the complete support matrix and defaults.

# LD-swap diagnostics and fine-mapping

LD-swap diagnostics are enabled through `updateLDswap = TRUE`. The fitted object
contains stable `ld_swap` and `ld_swap_chains` fields. If diagnostics are not
available or not applicable, these fields should be present with `NULL` values.

```r
fit_csr_ldswap <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesR",
  nit = 1000,
  nburn = 100,
  ncores = 4,
  seed = 10,
  updateLDswap = TRUE,
  ld_swap_prob = 0.50,
  ld_swap_r2 = 0.001,
  ld_swap_moves = 20
)

check_stblr_consistency(
  fit_csr_ldswap,
  require_ld_swap = TRUE
)

fit_csr_ldswap$ld_swap
```

Credible sets are post-processing outputs constructed from fitted model outputs
and LD information. They are not separate sampler return objects.

```r
cs <- make_credible_sets(
  fit = fit_csr_ldswap,
  Glist = Glist,
  trait = "D1",
  coverage = 0.95,
  min_r2 = 0.5,
  pip_cutoff = 0.001,
  locus_pip_cutoff = 0.01,
  max_locus_distance = 1e6,
  method = "pip"
)

cs$summary
cs$sets[[1]]
```

`make_credible_sets()` extracts marker PIPs from `fit$dm`, then uses supplied
dense `LD` or `Glist$sparseLD` slices to build regional credible sets. It accepts
optional marker `sets`; otherwise it defines loci around high-PIP markers. The
returned object contains `summary`, `sets`, `locus_sets`, `loci`, `parameters`,
and the resolved `trait`.

`make_credible_sets()` delegates per-locus set construction to
`make_credible_sets_from_ld()`. Within a locus, it repeatedly selects a lead
marker, forms a candidate set using LD to the lead marker, ranks candidate
members by PIP, and includes markers until the requested coverage is reached.
Because no maximum number of sets is exposed by `make_credible_sets()`, one locus
may produce multiple sets labelled `CS1`, `CS2`, and so on. With
`allow_incomplete = FALSE`, under-coverage attempts are dropped rather than
returned with an incomplete flag.

`extract_stblr_finemap_loci()` and `finemap_stblr_csr()` return their own
post-processing objects and may include credible-set outputs when requested, but
those are helper-level diagnostics, not native sampler return fields.

# Fixed and sampled selection_s

`selection_s` controls MAF-dependent prior scaling for supported CSR models. On
the standardized-genotype scale:

```text
q_j(S) = h_j^(S + 1),  h_j = 2 p_j (1 - p_j)
```

Fixed `selection_s` examples:

```r
fit_s_null <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesC",
  selection_s = NULL,
  nit = 1000,
  nburn = 100,
  seed = 10
)

fit_s_minus1 <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesC",
  selection_s = -1,
  nit = 1000,
  nburn = 100,
  seed = 10
)
```

# Stable formatted fit outputs

The public wrappers format native sampler results into named lists. Always
inspect `names(fit)` and the relevant help page because some components are
model-specific or optional. Formatted fit objects should preserve a stable public
structure across active backends.

Common fields include:

```text
bm, dm, wy, r, b, d,
vbs, vgs, ves, vle, vld,
pis, pi, pim,
covb, covg, cove,
input, chains,
ld_swap, ld_swap_chains,
selection_s*,
comp_prob,
dm_component_mean,
annotation/group/prior/component fields where relevant
```

| Component | Interpretation |
|---|---|
| `dm` | Posterior inclusion probability or non-null component probability, usually an `m x nt` matrix. |
| `bm` | Posterior mean marker effects, usually aligned with `dm`. |
| `b` | Current or returned marker-effect state, when returned. It is not the same as `bm`. |
| `d` | Current or returned inclusion/non-null state, when returned. It is not the same as `dm`. |
| `wy` | Marker-trait cross-products used by CSR models. |
| `r` | Current or returned marker-scale residual state, when returned. |
| `vbs`, `vgs`, `ves` | Active marker-effect, genetic, and residual variance traces/summaries. |
| `vle`, `vld` | LE/LD variance decomposition traces where available. |
| `pi`, `pim`, `pis` | Inclusion-probability summaries/traces where emitted by the backend. |
| `covb`, `covg`, `cove` | Marker-effect, genetic, and residual covariance summaries where returned. |
| `comp_prob` | BayesR/SBayesRC marker-level component probabilities. |
| `dm_component_mean` | Component-specific non-null summaries. |
| `input` | Model/backend/input metadata. |
| `chains` | Per-chain outputs when `keep_chains = TRUE`. |
| `ld_swap` | Trait-level LD-swap diagnostics when available. |
| `ld_swap_chains` | Chain-level LD-swap diagnostics when available. |

For checks after every fit:

```r
check_stblr_consistency(fit)
names(fit)
str(fit$input)
dim(fit$dm)
dim(fit$bm)
```

## Annotation-specific components

Annotation-aware fits add fields whose interpretation depends on the prior
family:

- Fixed-prior models may expose marker-specific prior inclusion probabilities,
  prior variance multipliers, and compact annotation summaries.
- Learned annotation models expose learned `eta_pi` and/or `eta_vb` quantities
  where those updates were enabled, together with acceptance summaries.
- Group models expose group-level inclusion and variance summaries, such as
  `group_pi`, `group_vb_multiplier`, and `group_nincluded` where returned.
- SBayesRC-style models expose annotation effects on component probabilities.
  The `alpha` fields describe annotation effects for probit stick-breaking steps,
  `sigmaSqAlpha` summarizes their variance parameters, `comp_prob` contains
  marker-level posterior component probabilities, and `ncomp` summarizes numbers
  of markers assigned to components.
- In CSR BayesR, the null component column is usually `component_0` and
  `dm = 1 - P(component_0)`.
- In CSR SBayesRC, the null component column is usually `gamma_0.00` and
  `dm = 1 - P(gamma_0.00)`.

These components have different dimensions and meanings. Do not compare an
`eta_pi` coefficient directly with an `alpha` coefficient without accounting for
their distinct links and prior structures.

# Compact reporting

Marker-level matrices can contain tens of thousands or millions of entries.
Printing `fit$bm`, `fit$dm`, `fit$b`, a full `comp_prob`, or the complete fit
object floods the console and obscures useful diagnostics. Full objects should
remain available for analysis and serialization, while routine reporting should
aggregate them deliberately.

A compact trait-level summary can include:

- number of markers and traits;
- sum of PIPs by trait, `colSums(fit$dm)`;
- mean absolute posterior effect, `colMeans(abs(fit$bm))`;
- means and selected quantiles of `vbs`, `vgs`, and `ves`;
- compact diagonal and off-diagonal covariance summaries when present.

For example:

```r
data.frame(
  trait = colnames(fit$dm),
  pip_sum = colSums(fit$dm),
  mean_abs_bm = colMeans(abs(fit$bm)),
  mean_vg = colMeans(fit$vgs),
  mean_ve = colMeans(fit$ves)
)
```

Treat `sum(PIP)` as an effective posterior number of included markers under the
fitted model, not as a known count of causal variants.

# PIPs and top-marker summaries

For marker `i` and trait `t`, `fit$dm[i, t]` represents PIP or non-null posterior
probability under the fitted likelihood, prior, and sampler. A useful top-marker
table contains marker identifier, trait, PIP, absolute posterior mean effect, and
signed posterior mean effect:

```r
ord <- order(-fit$dm[, 1], -abs(fit$bm[, 1]))
head(data.frame(
  marker = rownames(fit$dm),
  pip = fit$dm[, 1],
  abs_bm = abs(fit$bm[, 1]),
  bm = fit$bm[, 1]
)[ord, ], 10)
```

Rankings depend on LD, the marker set, priors, phenotype architecture,
summary-statistic quality, and MCMC settings. Correlated markers can share
posterior evidence, and an annotation-informed prior can change rankings even
when the likelihood is unchanged. Top markers are candidates for follow-up, not
automatically causal variants.

When comparing models, report whether the same markers, traits, LD, and MCMC
settings were used. Differences in rankings otherwise combine model effects with
input differences.

# Variance and covariance summaries

`vgs` and `ves` provide iteration-level genetic and residual variance summaries.
`vbs` tracks the active marker-effect variance scale used by the model. Report
posterior means together with quantiles or trace diagnostics, not only final
values.

In simulations, compare posterior genetic and residual variance summaries with
the generating architecture and requested `h2`. Do not expect exact recovery from
a short chain or finite simulated data. Realized simulated heritability,
sparse-LD approximation, prior shrinkage, and Monte Carlo variation all affect
the comparison.

For multiple traits, `covb`, `covg`, and `cove` summarize different covariance
targets when returned. Their off-diagonal entries should be interpreted only
after confirming that the fitted wrapper actually represents the intended joint
model. Parallel single-trait fits do not automatically become a fully joint
multi-trait analysis.

# Annotation-level diagnostics

Annotation diagnostics answer different questions depending on whether truth is
available and how annotation information enters the prior.

## Simulation truth and posterior summaries

For an `mtsim_annotation()` result:

```r
summarize_annotation_signal(sim)
summarize_annotation_signal(sim, fit)
```

The first call summarizes true annotation sizes and causal enrichment. The
second adds annotation-level mean PIP and mean absolute posterior effects for
each trait. Comparing these tables helps assess recovery in simulations, but does
not establish causal annotation effects in real data.

## Learned and group annotation fits

For learned models, inspect `eta_pi` and `eta_vb` together with posterior marker
summaries, annotation prevalence, and correlations among annotation columns.
Large coefficients can reflect true enrichment, overlap, collinearity, weak
regularization, or short-chain instability.

For group models, report group sizes alongside `group_pi`,
`group_vb_multiplier`, and `group_nincluded`. Small groups generally produce less
stable group-level summaries.

## SBayesRC-style prior-architecture diagnostics

The exported helpers convert SBayesRC-style annotation coefficients into
component probabilities and expected gamma multipliers:

- `sbayesrc_annotation_pi()` and `sbayesrc_annotation_gamma_mean()` summarize
  individual annotation coefficient rows;
- `sbayesrc_marker_pi()` and `sbayesrc_marker_gamma_mean()` combine complete
  marker annotation profiles with `alpha`.

Annotation-row summaries are not the same as marker-level predictions when
annotations overlap. A compact report can show the annotation-level expected
gamma table, `summary()` of marker expected gamma, and its correlation with PIP
by trait. These describe the fitted prior architecture and posterior
relationship; they are not proof that an annotation or marker is causal.

See [Technical annotation priors](technical_annotation_priors.html) and
[Technical SBayesRC-style annotations](technical_sbayesrc_annotations.html) for
the underlying prior structures.

# Demonstration versus production runs

The workflow scripts use short, often single-chain settings to test integration
and make iterative development feasible. A successful demonstration run shows
that inputs align, native samplers execute, and outputs can be formatted. It does
not establish convergence or robust inference.

Production analyses generally require:

- substantially longer burn-in and retained sampling;
- repeated chains or otherwise defensible convergence assessment;
- trace, mixing, effective-sample-size, and posterior predictive diagnostics;
- sensitivity analysis for prior settings and annotation regularization;
- sensitivity to LD thresholds, LD windows, scaling, and marker selection;
- reproducible seeds, software versions, and input provenance;
- held-out validation or cross-fitting where data-derived priors are reused.

No universal chain length can be recommended from the current workflows.
Required effort depends on marker count, sparsity, LD, prior complexity,
annotation collinearity, and the inferential target.

# Recommended validation and reporting checklist

For real analyses, run a small or moderate validation first and save:

- package git commit hash;
- model call;
- `sessionInfo()`;
- dimensions: markers, traits, samples if BED, LD nonzeros if available;
- `nit`, `nburn`, `nthin`, `nchains`, `ncores`;
- runtime and object size if available;
- `check_stblr_consistency(fit)`;
- key posterior summaries;
- warnings and diagnostics.

For each reported fit, also record:

- **Data source:** BED source or summary-statistics provenance, selected chromosomes/regions, marker count, and marker-order checks.
- **Samples and traits:** sample size `n`, selected sample rows, number of traits, phenotype preprocessing, and missingness handling.
- **LD construction:** source panel, `r2_threshold`, distance limits, scaling, block settings, and CSR prefix provenance.
- **Model and priors:** wrapper name, plain or annotation-informed prior, inclusion and variance-prior settings, annotation preprocessing, group definitions, gamma grid where relevant, and whether fixed global or sampled trait-specific `selection_s` was used.
- **MCMC settings:** `nit`, `nburn`, `nthin`, chains, seed, scheduling choices, and thread count.
- **Convergence caveat:** diagnostics performed and any limitations caused by short or single-chain runs.
- **Marker summaries:** PIP sums, top-marker table, and selected posterior effect summaries without dumping full matrices.
- **Variance summaries:** posterior means and uncertainty for genetic, residual, and active marker-effect variance quantities.
- **Annotation summaries:** annotation size, enrichment or learned coefficients, group summaries, or SBayesRC-style component diagnostics when relevant.
- **Validation and sensitivity:** BED-versus-CSR comparison, simulation truth, held-out prediction, prior sensitivity, and LD-threshold sensitivity as appropriate.

At minimum, inspect:

```r
check_stblr_consistency(fit)
summary(colMeans(fit$dm, na.rm = TRUE))
summary(colMeans(fit$bm, na.rm = TRUE))
summary(colMeans(fit$vgs, na.rm = TRUE))
summary(colMeans(fit$ves, na.rm = TRUE))
fit$ld_swap
```

For annotation-informed analyses, explicitly state that enrichment and posterior
prioritization are evidence structures rather than causal proof.

For large analyses, object size and trace storage may become the limiting factor.
Use the workflow examples to identify which fields are needed for the intended
post-processing before adding long chains or many traits.
