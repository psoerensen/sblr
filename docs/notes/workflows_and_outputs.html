Workflows and Outputs

Author
Affiliation

Peter Sørensen

Aarhus University

The workflow scripts in examples/workflows/ connect the model interfaces, data representations, and posterior outputs described elsewhere in these notes. They show the current sequence of package calls, the objects passed between layers, and compact ways to inspect fitted models.

These scripts are runnable demonstrations and validation templates. They are deliberately not automatically lightweight package examples: they may need external PLINK data, a prepared qgg Glist, local output paths, native code, multiple threads, and long MCMC runs. Both docs/ and examples/ are listed in .Rbuildignore, so they remain available in the GitHub repository and documentation site without becoming part of the installed package build.

The main scripts are:

  • examples/workflows/sparse_ld_bed_workflow.R, which connects direct individual-level BED fitting to BED-derived sufficient statistics and disk-backed sparse-LD CSR fitting;
  • examples/workflows/annotation_based_models.R, which builds on the same CSR foundation to compare four annotation-informed prior structures.

This note explains how to run those workflows deliberately, how to summarize their returned fit objects, and how to avoid interpreting demonstration output as final inference.

Workflow Decision Table

Question Starting data Principal workflow or function Main output

Choose the workflow from the available data and the intended prior, not from which script is shortest. The model map in Model overview separates data representation, trait structure, and prior structure.

Workflow Scripts as Executable Architecture Documents

A workflow script serves several roles at once:

  1. It demonstrates a complete object handoff across public functions.
  2. It records marker-order, sample-row, scaling, and LD settings that must remain consistent.
  3. It provides an integration check that independently developed package layers compose correctly.
  4. It supplies compact inspection patterns for objects that may contain tens of thousands of marker rows.

It does not replace function help, automated tests, or a study-specific analysis plan. Help pages define individual arguments. Tests should verify small deterministic contracts. Workflow scripts instead show how realistic, potentially expensive pieces are assembled.

Before running either workflow, replace its local data paths, confirm the selected sample and marker order, choose an LD output prefix that can be written safely, and decide whether the demonstration-scale MCMC settings are appropriate for the immediate purpose.

BED-Direct and Summary-Statistics CSR Workflow

sparse_ld_bed_workflow.R is the practical bridge between an individual-level BED model and a summary-statistics CSR model. The complete data and alignment contracts are documented in Sparse-LD and BED workflows.

Its stages are:

BED-backed Glist + phenotypes
    -> align LD markers with BED columns using cls
    -> optionally fit stblr_bed()
    -> compute stats with make_summary_stats()
    -> compute sparse LD with make_sparse_ld()
    -> fit stblr_csr()
    -> compare BED and CSR summaries cautiously

Prepare BED, Glist, and Phenotype Inputs

The workflow loads a qgg Glist, selects chromosomes and markers, and obtains or simulates a phenotype matrix. mtsim() is useful for integration checks because its returned effects and causal markers provide known truth. In a real analysis, phenotypes and covariate adjustment must instead follow the study’s analysis plan.

The script maps selected LD-marker identifiers back to BED marker columns:

cls <- match(Glist$rsidsLD[[chr]], Glist$rsids[[chr]])
stopifnot(!anyNA(cls))

This is a correctness check, not bookkeeping. The same selected markers and order must be used for BED fitting, sufficient statistics, sparse LD, and posterior interpretation.

Optionally Fit the Direct BED Model

stblr_bed() reads marker data from BED files during fitting. It is the direct individual-level comparison path and does not need a separately prepared sparse-LD artifact.

Use it when individual-level genotypes remain available and direct marker updates are desired. Record the selected rows, cls, scaling choice, prior settings, scheduling controls, seed, and MCMC settings. These choices matter when comparing its output with a CSR fit.

Compute Sufficient Statistics and Sparse LD

make_summary_stats() computes the marker-trait and phenotype cross-products used by the CSR model from a BED-backed Glist. The important returned quantities include:

  • stats$wy, corresponding to marker-trait cross-products;
  • stats$ww, containing marker diagonal cross-products;
  • stats$yy, containing phenotype sums of squares;
  • metadata such as marker count, trait count, and sample size when available.

make_sparse_ld() then writes thresholded sparse LD from the same BED-backed Glist and stores the sparse-LD prefix, selected chromosomes, marker columns, allele frequencies, rows, threshold, window, and block metadata in Glist$sparseLD. Its r2_threshold, distance limits, selected rows, allele frequencies, marker columns, and scaling assumptions should be reported. sparseLD_read_CSR() can inspect the resulting representation, but users should rely on package readers and writers rather than treating the on-disk files as a stable manual file-format API.

Fit and Compare the CSR Model

stblr_csr() combines stats with the sparse-LD metadata in Glist. A short call is:

fit_csr <- stblr_csr(
  stats = stats,
  Glist = Glist,
  method = "bayesC",
  nit = 1000,
  nburn = 100,
  seed = 10
)

Matched BED and CSR fits should agree qualitatively when marker order, selected rows, genotype scaling, priors, and MCMC settings match. Exact equality is not expected. Sparse-LD thresholding, residual representation, update scheduling, floating-point behavior, and Monte Carlo variation can all produce differences. Compare posterior effects, PIPs, and variance summaries; do not treat equality of individual draws as a validation target.

Annotation-Model Comparison Workflow

annotation_based_models.R starts from the same BED-to-CSR preparation path, then compares annotation prior families while holding stats, sparse LD, and marker order fixed.

Its stages are:

mtsim_annotation()
    -> summarize_annotation_signal()
    -> make_summary_stats()
    -> make_sparse_ld()
    -> align annotation matrix A
    -> fit fixed, learned, group, and SBayesRC-style CSR models with stblr_csr_annot()
    -> compact fit, marker, variance, and annotation summaries

Simulate and Inspect Annotation Signal

mtsim_annotation() simulates multi-trait phenotypes, marker effects, overlapping annotation memberships, enriched causal-marker sampling, and marker-specific prior values. It is useful because the annotation architecture and causal markers are known.

Before fitting, summarize_annotation_signal(sim) reports annotation size, causal-marker counts, and causal rates. These are truth-aware simulation diagnostics. They are unavailable in real data, where causal membership is not known.

Prepare Shared CSR Inputs and Align A

The workflow computes sufficient statistics and streams sparse LD exactly as in the plain CSR workflow. It then constructs an \(m \times K\) annotation matrix A, where rows are markers and columns are annotations.

rownames(A) <- marker_id
stopifnot(nrow(A) == length(cls), identical(rownames(A), marker_id))

The alignment check is essential. Row \(i\) of A must describe the same marker as row \(i\) of stats$wy, stats$ww, the sparse-LD rows and columns, and the returned marker-level posterior summaries.

Fit Four Annotation Prior Families

The script fits:

  1. stblr_csr_annot(annotation_model = "prior") with fixed marker-specific inclusion probabilities and variance multipliers;
  2. stblr_csr_annot(annotation_model = "learned") with annotation effects learned during fitting;
  3. stblr_csr_annot(annotation_model = "group") with mutually exclusive group-level priors;
  4. stblr_csr_annot(annotation_model = "sbayesrc") with an SBayesRC-style annotation-dependent BayesR prior.

The compatibility wrappers stblr_csr_prior_annot(), stblr_csr_learn_annot(), stblr_csr_group_annot(), and stblr_csr_sbayesrc_generic() remain supported.

The fourth model uses annotation-dependent probit stick-breaking probabilities over an exact null and multiple active variance components. It is not an exact reproduction of the published GCTB SBayesRC implementation as exposed by default: sblr uses a CSR sparse-LD likelihood and defaults to gamma = c(0, 0.01, 0.1, 1). Users who want the published gamma grid can supply:

gamma = c(0, 0.001, 0.01, 0.1, 1)

Matching that grid aligns one part of the prior specification; it does not make the complete implementation identical to GCTB SBayesRC. See Annotation-informed models for the model comparison.

CSR SBayesRC also supports optional BayesS-style selection_s. In this model, annotations affect component probabilities and selection_s affects marker-specific effect-size prior variance. Sampled trait-specific selection_s is requested through the unified annotation interface:

fitS <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = annotations,
  annotation_model = "sbayesrc",
  estimate_selection_s = TRUE
)

Sampled selection_s is not supported for annotation_model = "prior", "learned", or "group". See selection_s implementation status for the complete support matrix and defaults.

Fit Object Structure

The public wrappers format native sampler results into named lists. Always inspect names(fit) and the relevant help page because some components are model-specific or optional.

Component Interpretation
dm Posterior inclusion probability or non-null component probability, usually an \(m \times n_t\) matrix.
bm Posterior mean marker effects, usually aligned with dm.
b Current or returned marker-effect state, when returned. It is not the same as bm.
r Current or returned marker-scale residual state, when returned.
vbs MCMC trace of marker-effect variance scale.
vgs MCMC trace of genetic variance summaries.
ves MCMC trace of residual variance summaries.
vle MCMC trace of linkage-equilibrium variance contribution, where returned.
vld MCMC trace of LD variance contribution, where returned.
covb Posterior marker-effect covariance summary, when returned.
covg Posterior genetic covariance summary, when returned.
cove Posterior residual covariance summary, when returned.
pi Final or current inclusion-probability summary, with exact meaning determined by the wrapper.
pim Posterior mean inclusion-probability summary, when returned.
input Resolved model inputs, preprocessing choices, priors, and MCMC settings added by public wrappers.
chains Optional compact chain-level summaries when keep_chains = TRUE and supported.

Some fits additionally return correlation versions rb, rg, and re when the corresponding covariance matrices are valid.

Sampled selection_s fits return selection_s, selection_s_sd, selection_s_min, selection_s_max, selection_s_trace, and selection_s_acceptance. The trace is an iteration-by-trait matrix, selection_s is the posterior mean by trait, and selection_s_acceptance is the MH acceptance rate by trait. With keep_chains = TRUE, compact chain objects contain selection_s and selection_s_acceptance for each trait and chain.

Annotation-Specific Components

  • Annotation-aware fits expose standardized aliases where available: annotation_summary, annotation_pi, annotation_effects, annotation_prior, alpha, and sigmaSqAlpha.
  • Learned-annotation fits also return eta_pi and eta_vb, summarizing annotation effects on inclusion probabilities and variance multipliers.
  • Group fits also return group_pi, group_vb_multiplier, group_nincluded, and group_size.
  • SBayesRC-style fits return alpha, sigmaSqAlpha, comp_prob, and ncomp. Here alpha contains annotation coefficients for stick-breaking steps, sigmaSqAlpha summarizes their variance parameters, comp_prob contains marker-level posterior component probabilities, and ncomp summarizes numbers of markers assigned to components.
  • In CSR BayesR, the null component column is component_0 and dm = 1 - P(component_0).
  • In CSR SBayesRC, the null component column is gamma_0.00 and dm = 1 - P(gamma_0.00).

These components have different dimensions and meanings. Do not compare an eta_pi coefficient directly with an alpha coefficient without accounting for their distinct links and prior structures.

Compact Reporting

Marker-level matrices can contain tens of thousands or millions of entries. Printing fit$bm, fit$dm, fit$b, a full comp_prob, or the complete fit object floods the console and obscures useful diagnostics. Full objects should remain available for analysis and serialization, while routine reporting should aggregate them deliberately.

A compact trait-level summary can include:

  • number of markers and traits;
  • sum of PIPs by trait, colSums(fit$dm);
  • mean absolute posterior effect, colMeans(abs(fit$bm));
  • means and selected quantiles of vbs, vgs, and ves;
  • compact diagonal and off-diagonal covariance summaries when present.

For example:

data.frame(
  trait = colnames(fit$dm),
  pip_sum = colSums(fit$dm),
  mean_abs_bm = colMeans(abs(fit$bm)),
  mean_vg = colMeans(fit$vgs),
  mean_ve = colMeans(fit$ves)
)

Treat sum(PIP) as an effective posterior number of included markers under the fitted model, not as a known count of causal variants.

PIPs and Top-Marker Summaries

For marker \(i\) and trait \(t\), fit$dm[i, t] represents PIP or non-null posterior probability under the fitted likelihood, prior, and sampler. A useful top-marker table contains marker identifier, trait, PIP, absolute posterior mean effect, and signed posterior mean effect:

ord <- order(-fit$dm[, 1], -abs(fit$bm[, 1]))
head(data.frame(
  marker = rownames(fit$dm),
  pip = fit$dm[, 1],
  abs_bm = abs(fit$bm[, 1]),
  bm = fit$bm[, 1]
)[ord, ], 10)

Rankings depend on LD, the marker set, priors, phenotype architecture, summary-statistic quality, and MCMC settings. Correlated markers can share posterior evidence, and an annotation-informed prior can change rankings even when the likelihood is unchanged. Top markers are candidates for follow-up, not automatically causal variants.

When comparing models, report whether the same markers, traits, LD, and MCMC settings were used. Differences in rankings otherwise combine model effects with input differences.

Fine-Mapping, LD-Swap, and Credible Sets

Fine-mapping diagnostics are layered on top of fit outputs. PIP is represented by fit$dm. When updateLDswap = TRUE and the backend supports it, LD-swap diagnostics are represented by fit$ld_swap and chain-level ld_swap outputs such as fit$ld_swap_chains or compact entries in fit$chains.

Credible sets are constructed by helper functions rather than returned as core sampler objects. make_credible_sets() extracts marker PIPs from fit$dm, then uses supplied dense LD or Glist$sparseLD$prefix to build regional credible sets. It accepts optional marker sets; otherwise it defines loci around high-PIP markers. The returned object contains summary, sets, locus_sets, loci, parameters, and the resolved trait.

extract_stblr_finemap_loci() and finemap_stblr_csr() return their own post-processing objects and may include credible-set outputs when requested, but those are helper-level diagnostics, not native sampler return fields.

Variance and Covariance Summaries

vgs and ves provide iteration-level genetic and residual variance summaries. vbs tracks the active marker-effect variance scale used by the model. Report posterior means together with quantiles or trace diagnostics, not only final values.

In simulations, compare posterior genetic and residual variance summaries with the generating architecture and requested h2. Do not expect exact recovery from a short chain or finite simulated data. Realized simulated heritability, sparse-LD approximation, prior shrinkage, and Monte Carlo variation all affect the comparison.

For multiple traits, covb, covg, and cove summarize different covariance targets when returned. Their off-diagonal entries should be interpreted only after confirming that the fitted wrapper actually represents the intended joint model. Parallel single-trait fits do not automatically become a fully joint multi-trait analysis.

Annotation-Level Diagnostics

Annotation diagnostics answer different questions depending on whether truth is available and how annotation information enters the prior.

Simulation Truth and Posterior Summaries

For an mtsim_annotation() result:

summarize_annotation_signal(sim)
summarize_annotation_signal(sim, fit)

The first call summarizes true annotation sizes and causal enrichment. The second adds annotation-level mean PIP and mean absolute posterior effects for each trait. Comparing these tables helps assess recovery in simulations, but does not establish causal annotation effects in real data.

Learned and Group Annotation Fits

For learned models, inspect eta_pi and eta_vb together with posterior marker summaries, annotation prevalence, and correlations among annotation columns. Large coefficients can reflect true enrichment, overlap, collinearity, weak regularization, or short-chain instability.

For group models, report group sizes alongside group_pi, group_vb_multiplier, and group_nincluded. Small groups generally produce less stable group-level summaries.

SBayesRC-Style Prior-Architecture Diagnostics

The exported helpers convert SBayesRC-style annotation coefficients into component probabilities and expected gamma multipliers:

  • sbayesrc_annotation_pi() and sbayesrc_annotation_gamma_mean() summarize individual annotation coefficient rows;
  • sbayesrc_marker_pi() and sbayesrc_marker_gamma_mean() combine complete marker annotation profiles with alpha.

Annotation-row summaries are not the same as marker-level predictions when annotations overlap. A compact report can show the annotation-level expected gamma table, summary() of marker expected gamma, and its correlation with PIP by trait. These describe the fitted prior architecture and posterior relationship; they are not proof that an annotation or marker is causal.

See Technical annotation priors and Technical SBayesRC-style annotations for the underlying prior structures.

Demonstration Versus Production Runs

The workflow scripts use short, single-chain settings to test integration and make iterative development feasible. A successful demonstration run shows that inputs align, native samplers execute, and outputs can be formatted. It does not establish convergence or robust inference.

Production analyses generally require:

  • substantially longer burn-in and retained sampling;
  • repeated chains or otherwise defensible convergence assessment;
  • trace, mixing, effective-sample-size, and posterior predictive diagnostics;
  • sensitivity analysis for prior settings and annotation regularization;
  • sensitivity to LD thresholds, LD windows, scaling, and marker selection;
  • reproducible seeds, software versions, and input provenance;
  • held-out validation or cross-fitting where data-derived priors are reused.

No universal chain length can be recommended from the current workflows. Required effort depends on marker count, sparsity, LD, prior complexity, annotation collinearity, and the inferential target.

Recommended Reporting Checklist

For each reported fit, record:

  • Data source: BED source or summary-statistics provenance, selected chromosomes/regions, marker count, and marker-order checks.
  • Samples and traits: sample size n, selected sample rows, number of traits, phenotype preprocessing, and missingness handling.
  • LD construction: source panel, r2_threshold, distance limits, scaling, block settings, and CSR prefix provenance.
  • Model and priors: wrapper name, plain or annotation-informed prior, inclusion and variance-prior settings, annotation preprocessing, group definitions, gamma grid where relevant, and whether fixed global or sampled trait-specific selection_s was used.
  • MCMC settings: nit, nburn, nthin, chains, seed, scheduling choices, and thread count.
  • Convergence caveat: diagnostics performed and any limitations caused by short or single-chain runs.
  • Marker summaries: PIP sums, top-marker table, and selected posterior effect summaries without dumping full matrices.
  • Variance summaries: posterior means and uncertainty for genetic, residual, and active marker-effect variance quantities.
  • Annotation summaries: annotation size, enrichment or learned coefficients, group summaries, or SBayesRC-style component diagnostics when relevant.
  • Validation and sensitivity: BED-versus-CSR comparison, simulation truth, held-out prediction, prior sensitivity, and LD-threshold sensitivity as appropriate.

For annotation-informed analyses, explicitly state that enrichment and posterior prioritization are evidence structures rather than causal proof.

The script fits:

1. `stblr_csr_annot(annotation_model = "prior")` with fixed marker-specific
   inclusion probabilities and variance multipliers;
2. `stblr_csr_annot(annotation_model = "learned")` with annotation effects
   learned during fitting;
3. `stblr_csr_annot(annotation_model = "group")` with mutually exclusive
   group-level priors;
4. `stblr_csr_annot(annotation_model = "sbayesrc")` with an
   **SBayesRC-style annotation-dependent BayesR prior**.

The compatibility wrappers `stblr_csr_prior_annot()`,
`stblr_csr_learn_annot()`, `stblr_csr_group_annot()`, and
`stblr_csr_sbayesrc_generic()` remain supported.

The fourth model uses annotation-dependent probit stick-breaking probabilities
over an exact null and multiple active variance components. It is not an exact
reproduction of the published GCTB SBayesRC implementation as exposed by
default: `sblr` uses a CSR sparse-LD likelihood and defaults to
`gamma = c(0, 0.01, 0.1, 1)`. Users who want the published gamma grid can
supply:

```r
gamma = c(0, 0.001, 0.01, 0.1, 1)
```

Matching that grid aligns one part of the prior specification; it does not
make the complete implementation identical to GCTB SBayesRC. See
[Annotation-informed models](annotation_informed_models.html) for the model
comparison.

CSR SBayesRC also supports optional BayesS-style `selection_s`. In this model,
annotations affect component probabilities and `selection_s` affects
marker-specific effect-size prior variance. Sampled trait-specific
`selection_s` is requested through the unified annotation interface:

```r
fitS <- stblr_csr_annot(
  stats = stats,
  Glist = Glist,
  annotations = annotations,
  annotation_model = "sbayesrc",
  estimate_selection_s = TRUE
)
```

Sampled `selection_s` is not supported for `annotation_model = "prior"`,
`"learned"`, or `"group"`. See
[selection_s implementation status](selection_s_status.md) for the complete
support matrix and defaults.

## Fit Object Structure

The public wrappers format native sampler results into named lists. Always
inspect `names(fit)` and the relevant help page because some components are
model-specific or optional.

| Component | Interpretation |
|---|---|
| `dm` | Posterior inclusion probability or non-null component probability, usually an $m \times n_t$ matrix. |
| `bm` | Posterior mean marker effects, usually aligned with `dm`. |
| `b` | Current or returned marker-effect state, when returned. It is not the same as `bm`. |
| `r` | Current or returned marker-scale residual state, when returned. |
| `vbs` | MCMC trace of marker-effect variance scale. |
| `vgs` | MCMC trace of genetic variance summaries. |
| `ves` | MCMC trace of residual variance summaries. |
| `vle` | MCMC trace of linkage-equilibrium variance contribution, where returned. |
| `vld` | MCMC trace of LD variance contribution, where returned. |
| `covb` | Posterior marker-effect covariance summary, when returned. |
| `covg` | Posterior genetic covariance summary, when returned. |
| `cove` | Posterior residual covariance summary, when returned. |
| `pi` | Final or current inclusion-probability summary, with exact meaning determined by the wrapper. |
| `pim` | Posterior mean inclusion-probability summary, when returned. |
| `input` | Resolved model inputs, preprocessing choices, priors, and MCMC settings added by public wrappers. |
| `chains` | Optional compact chain-level summaries when `keep_chains = TRUE` and supported. |

Some fits additionally return correlation versions `rb`, `rg`, and `re` when
the corresponding covariance matrices are valid.

Sampled `selection_s` fits return `selection_s`, `selection_s_sd`,
`selection_s_min`, `selection_s_max`, `selection_s_trace`, and
`selection_s_acceptance`. The trace is an iteration-by-trait matrix,
`selection_s` is the posterior mean by trait, and `selection_s_acceptance` is
the MH acceptance rate by trait. With `keep_chains = TRUE`, compact chain
objects contain `selection_s` and `selection_s_acceptance` for each trait and
chain.

### Annotation-Specific Components

- Annotation-aware fits expose standardized aliases where available:
  `annotation_summary`, `annotation_pi`, `annotation_effects`,
  `annotation_prior`, `alpha`, and `sigmaSqAlpha`.
- Learned-annotation fits also return `eta_pi` and `eta_vb`, summarizing
  annotation effects on inclusion probabilities and variance multipliers.
- Group fits also return `group_pi`, `group_vb_multiplier`,
  `group_nincluded`, and `group_size`.
- SBayesRC-style fits return `alpha`, `sigmaSqAlpha`, `comp_prob`, and
  `ncomp`. Here `alpha` contains annotation coefficients for stick-breaking
  steps, `sigmaSqAlpha` summarizes their variance parameters, `comp_prob`
  contains marker-level posterior component probabilities, and `ncomp`
  summarizes numbers of markers assigned to components.
- In CSR BayesR, the null component column is `component_0` and
  `dm = 1 - P(component_0)`.
- In CSR SBayesRC, the null component column is `gamma_0.00` and
  `dm = 1 - P(gamma_0.00)`.

These components have different dimensions and meanings. Do not compare an
`eta_pi` coefficient directly with an `alpha` coefficient without accounting
for their distinct links and prior structures.

## Compact Reporting

Marker-level matrices can contain tens of thousands or millions of entries.
Printing `fit$bm`, `fit$dm`, `fit$b`, a full `comp_prob`, or the complete fit
object floods the console and obscures useful diagnostics. Full objects should
remain available for analysis and serialization, while routine reporting
should aggregate them deliberately.

A compact trait-level summary can include:

- number of markers and traits;
- sum of PIPs by trait, `colSums(fit$dm)`;
- mean absolute posterior effect, `colMeans(abs(fit$bm))`;
- means and selected quantiles of `vbs`, `vgs`, and `ves`;
- compact diagonal and off-diagonal covariance summaries when present.

For example:

```r
data.frame(
  trait = colnames(fit$dm),
  pip_sum = colSums(fit$dm),
  mean_abs_bm = colMeans(abs(fit$bm)),
  mean_vg = colMeans(fit$vgs),
  mean_ve = colMeans(fit$ves)
)
```

Treat `sum(PIP)` as an effective posterior number of included markers under
the fitted model, not as a known count of causal variants.

## PIPs and Top-Marker Summaries

For marker $i$ and trait $t$, `fit$dm[i, t]` represents PIP or non-null
posterior probability under the fitted likelihood, prior, and sampler. A
useful top-marker table contains marker identifier, trait, PIP, absolute
posterior mean effect, and signed posterior mean effect:

```r
ord <- order(-fit$dm[, 1], -abs(fit$bm[, 1]))
head(data.frame(
  marker = rownames(fit$dm),
  pip = fit$dm[, 1],
  abs_bm = abs(fit$bm[, 1]),
  bm = fit$bm[, 1]
)[ord, ], 10)
```

Rankings depend on LD, the marker set, priors, phenotype architecture,
summary-statistic quality, and MCMC settings. Correlated markers can share
posterior evidence, and an annotation-informed prior can change rankings even
when the likelihood is unchanged. Top markers are candidates for follow-up,
not automatically causal variants.

When comparing models, report whether the same markers, traits, LD, and MCMC
settings were used. Differences in rankings otherwise combine model effects
with input differences.

## Fine-Mapping, LD-Swap, and Credible Sets

Fine-mapping diagnostics are layered on top of fit outputs. PIP is represented
by `fit$dm`. When `updateLDswap = TRUE` and the backend supports it, LD-swap
diagnostics are represented by `fit$ld_swap` and chain-level `ld_swap` outputs
such as `fit$ld_swap_chains` or compact entries in `fit$chains`.

Credible sets are constructed by helper functions rather than returned as core
sampler objects. `make_credible_sets()` extracts marker PIPs from
`fit$dm`, then uses supplied dense `LD` or `Glist$sparseLD$prefix` to build
regional credible sets. It accepts optional marker `sets`; otherwise it
defines loci around high-PIP markers. The returned object contains `summary`,
`sets`, `locus_sets`, `loci`, `parameters`, and the resolved `trait`.

`extract_stblr_finemap_loci()` and `finemap_stblr_csr()` return their own
post-processing objects and may include credible-set outputs when requested,
but those are helper-level diagnostics, not native sampler return fields.

## Variance and Covariance Summaries

`vgs` and `ves` provide iteration-level genetic and residual variance
summaries. `vbs` tracks the active marker-effect variance scale used by the
model. Report posterior means together with quantiles or trace diagnostics,
not only final values.

In simulations, compare posterior genetic and residual variance summaries with
the generating architecture and requested `h2`. Do not expect exact recovery
from a short chain or finite simulated data. Realized simulated heritability,
sparse-LD approximation, prior shrinkage, and Monte Carlo variation all affect
the comparison.

For multiple traits, `covb`, `covg`, and `cove` summarize different covariance
targets when returned. Their off-diagonal entries should be interpreted only
after confirming that the fitted wrapper actually represents the intended
joint model. Parallel single-trait fits do not automatically become a fully
joint multi-trait analysis.

## Annotation-Level Diagnostics

Annotation diagnostics answer different questions depending on whether truth
is available and how annotation information enters the prior.

### Simulation Truth and Posterior Summaries

For an `mtsim_annotation()` result:

```r
summarize_annotation_signal(sim)
summarize_annotation_signal(sim, fit)
```

The first call summarizes true annotation sizes and causal enrichment. The
second adds annotation-level mean PIP and mean absolute posterior effects for
each trait. Comparing these tables helps assess recovery in simulations, but
does not establish causal annotation effects in real data.

### Learned and Group Annotation Fits

For learned models, inspect `eta_pi` and `eta_vb` together with posterior
marker summaries, annotation prevalence, and correlations among annotation
columns. Large coefficients can reflect true enrichment, overlap,
collinearity, weak regularization, or short-chain instability.

For group models, report group sizes alongside `group_pi`,
`group_vb_multiplier`, and `group_nincluded`. Small groups generally produce
less stable group-level summaries.

### SBayesRC-Style Prior-Architecture Diagnostics

The exported helpers convert SBayesRC-style annotation coefficients into
component probabilities and expected gamma multipliers:

- `sbayesrc_annotation_pi()` and `sbayesrc_annotation_gamma_mean()` summarize
  individual annotation coefficient rows;
- `sbayesrc_marker_pi()` and `sbayesrc_marker_gamma_mean()` combine complete
  marker annotation profiles with `alpha`.

Annotation-row summaries are not the same as marker-level predictions when
annotations overlap. A compact report can show the annotation-level expected
gamma table, `summary()` of marker expected gamma, and its correlation with
PIP by trait. These describe the fitted prior architecture and posterior
relationship; they are not proof that an annotation or marker is causal.

See [Technical annotation priors](technical_annotation_priors.html) and
[Technical SBayesRC-style annotations](technical_sbayesrc_annotations.html)
for the underlying prior structures.

## Demonstration Versus Production Runs

The workflow scripts use short, single-chain settings to test integration and
make iterative development feasible. A successful demonstration run shows
that inputs align, native samplers execute, and outputs can be formatted. It
does not establish convergence or robust inference.

Production analyses generally require:

- substantially longer burn-in and retained sampling;
- repeated chains or otherwise defensible convergence assessment;
- trace, mixing, effective-sample-size, and posterior predictive diagnostics;
- sensitivity analysis for prior settings and annotation regularization;
- sensitivity to LD thresholds, LD windows, scaling, and marker selection;
- reproducible seeds, software versions, and input provenance;
- held-out validation or cross-fitting where data-derived priors are reused.

No universal chain length can be recommended from the current workflows.
Required effort depends on marker count, sparsity, LD, prior complexity,
annotation collinearity, and the inferential target.

## Recommended Reporting Checklist

For each reported fit, record:

- **Data source:** BED source or summary-statistics provenance, selected
  chromosomes/regions, marker count, and marker-order checks.
- **Samples and traits:** sample size `n`, selected sample rows, number of
  traits, phenotype preprocessing, and missingness handling.
- **LD construction:** source panel, `r2_threshold`, distance limits, scaling,
  block settings, and CSR prefix provenance.
- **Model and priors:** wrapper name, plain or annotation-informed prior,
  inclusion and variance-prior settings, annotation preprocessing, group
  definitions, gamma grid where relevant, and whether fixed global or sampled
  trait-specific `selection_s` was used.
- **MCMC settings:** `nit`, `nburn`, `nthin`, chains, seed, scheduling choices,
  and thread count.
- **Convergence caveat:** diagnostics performed and any limitations caused by
  short or single-chain runs.
- **Marker summaries:** PIP sums, top-marker table, and selected posterior
  effect summaries without dumping full matrices.
- **Variance summaries:** posterior means and uncertainty for genetic,
  residual, and active marker-effect variance quantities.
- **Annotation summaries:** annotation size, enrichment or learned
  coefficients, group summaries, or SBayesRC-style component diagnostics when
  relevant.
- **Validation and sensitivity:** BED-versus-CSR comparison, simulation truth,
  held-out prediction, prior sensitivity, and LD-threshold sensitivity as
  appropriate.

For annotation-informed analyses, explicitly state that enrichment and
posterior prioritization are evidence structures rather than causal proof.
